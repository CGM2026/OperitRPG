# 02 存储、长期记忆、NPC 与旧版兼容

状态：待实施。存储 Agent 负责 schema、事务、备份和迁移样本；记忆/NPC 逻辑遵守同一数据契约。

## 两套引擎，明确路由

旧 rpg-v1.db 保持 schema1，旧 rpg_campaign 表及 recordJson 不因升级被改写。旧 CampaignRecord、Plan、ActionDefinition、默认值、JSON 设置、RainyDock 资源原始字节、planHash/actionHash 算法和 format1 备份都冻结。旧库仍可正常写入旧玩法的进度，“冻结”不等于只读。

新增 rpg-agent.db，初始 schema1，供新增长团引擎使用。选择独立数据库是为了避免首次长团重构触碰已发布数据库结构，也避免向严格解码的旧 JSON 填入新字段。以后新库演进仍需显式 Room migration 和旧 schema 测试，不使用删库重建。Android 官方说明破坏性迁移会永久删除数据，不能作为兼容策略：[Room migration](https://developer.android.com/training/data-storage/room/migrating-db-versions)。

统一标识 CampaignRef(engineId, campaignId)，engineId 固定为 legacy-rainydock-v1 或 longform-v1。列表合并两库的轻量标题/时间/引擎投影，打开后只交给明确对应的引擎。不能用“尝试新版解析，失败再按旧版解析”猜格式。

旧 DAO 增加只查询 id/title/updatedAt 的分页投影，不改 schema；旧存档仅在打开或明确导出时解码。移除 UI 启动时对全部战役逐个 recover 的做法：只处理被打开战役的中断请求。新库用单独 turn 索引读取未完成回合。

新选中状态保存 CampaignRef。首次升级时，旧 rpg-ui 的 campaign 值明确映射为 legacy 引擎；保留旧 key，不覆盖旧模型偏好。两个库不做跨库状态事务，新引擎一次结算的所有写入都发生在新库。

旧战役继续原玩法，旧进行中回合继续原协议；新 Agent 的导入模组、自由行动和 NPC 模拟只用于新引擎战役。本版不自动转换旧战役。它们可以从同一个首页访问。

## 新库实体与约束

核心实体：

- campaign：engineVersion、module/rules 精确版本与 hash、角色、当前场景、revision、lastEventSeq、模型绑定及创建/更新时间
- turn：campaignId、ordinal、clientMessageId、baseRevision、phase、冻结计划/hash、确认状态和结果引用
- model_attempt：attemptId、turnId、用途、配置指纹、状态、usage 和耗时；不保存 Key 或完整原始请求正文
- event：campaignId、seq、turnId、eventVersion、类型化效果、骰点、来源、可见范围及时间
- narration：turnId、已校验的公开正文及生成 attempt
- entity_state、inventory、objective_state：世界当前投影，可由初始状态与事件重放校验
- npc_state、npc_relation、npc_goal：人物状态和有类型的关系/目标
- fact、knowledge_edge、claim：正式事实、知情关系与未证实说法分开存储
- memory_note、summary、summary_source、derived_job：可修正笔记、摘要及其来源与任务状态
- module_revision、module_source_part、rule_chunk、memory_chunk、FTS 索引：不可变内容版本与可重建索引

数据库约束至少包含 UNIQUE(campaignId,clientMessageId)、UNIQUE(campaignId,ordinal)、UNIQUE(campaignId,eventSeq)、UNIQUE(turnId,commitKind) 和事实/人物引用外键。每个战役同时最多一个未结束回合；通过事务中的条件更新/唯一 pending 引用控制，不能只依赖 UI 禁用按钮。

业务实体只存当前需要的字段，不把每个回合重复塞入完整世界。事件记录足够重放的已结算效果及骰点，而不是只记动作名。列表、历史与检索分别分页。

文本模组内容采用不可变分块持久存储，单 part 不超过 64 KiB，避免单个数据库字段或 Cursor 装入整部文档。预览在临时区完成；激活时原文分块、模组元数据和 READY 状态在同一新库事务提交。失败回滚，暂存文件可清理，已引用正文不会被清理。

## 结算与恢复

一次世界结算事务依次检查阶段、revision、计划与模组/rule hash，生成必要骰点，写事件，更新角色/NPC/物品/事实投影，存结果，推进到 COMMITTED。任一写入失败整笔回滚。

网络和模型调用不能发生在数据库事务中。模型返回时检查 attemptId、阶段和版本，迟到结果不得覆盖已经取消、纠正或推进的战役。

COMMITTED 后旁白失败只能重试旁白，不能再次执行效果。未提交的计划可以取消；已经提交的结果不能因“停止生成”被撤销。若需要改历史，另做显式修订或分支方案，本版不提供隐式回滚。

各阶段和每次专用工具调用均有持久化 ID。应用重启标记未完成的网络请求为 INTERRUPTED，向用户展示继续/取消；不在后台静默重发付费请求。派生索引重建是本地任务，可恢复；付费摘要任务遵守独立任务设置和重试边界。

## 长期记忆的四层

第一层是正式世界状态：生命、地点、物品、目标、关系和已成立事实。由结算事件产生，是计算和回答当前状态的依据。

第二层是历史事件及对话：发生过的行动、骰点、承诺和人物发言。原始记录保留，人物发言本身是真实发生的事件，但发言内容未必是真实世界事实。

第三层是可检索的情节记忆：带 actor/entity IDs、发生时间、来源回合、有效期、可见范围及状态的条目。重要承诺和未完成目标不只埋在摘要中，拥有结构化记录。

第四层是章节摘要：提供阅读和上下文压缩，记录 sourceFromSeq/sourceToSeq、来源版本与摘要模型。摘要只能引用原记录，不能把新人物或新结论写成正式事实。模型抽取的非机械事实先成为待校验候选/说法；证据支持并符合类型约束后才激活，重大世界更正需要用户确认。

每轮上下文始终按相同策略装配：当前场景与活动实体的必要状态、未完成目标、近期回合、按当前问题检索的旧记录、有效摘要。不会无限追加全文，也不会把全部历史只压成一段不断覆盖的摘要。

摘要在章节结束或每 20 个完成回合形成待处理任务；生成可由用户启用的战役设置触发，每个来源窗口只产生一个有效版本。失败保存任务状态，不改变世界结算；事件、事实和索引仍然完整可查询。用户可明确重试。摘要从未覆盖到的事件不能被当作已纳入摘要。

纠错通过 CorrectionEvent、supersedesId 和来源版本完成。旧条目不删除，相关摘要标记失效，FTS 事务更新；后续检索默认只返回有效条目，历史查询可查看更正链。修改“记事”不能直接改骰点、HP、位置或物品。

预算以有限上下文为约束：默认每次输入最多 12,000 个估算 token，预留输出预算，由配置上限约束。估算和供应商 usage 分开显示。先移除低相关检索片段和冗余旧对话，保留当轮规则、角色权限、当前结算和关键状态；必要部分仍超限时明确中止并要求缩小任务，不静默遗漏必需约束。

## NPC 状态与知识

每个 NPC 保存身份/性格、位置、当前状态、目标、计划时点、关系维度、已知事实、信念、承诺与来源。关系使用限定字段与范围，不接受任意 JSON patch。

knowledge_edge 保存 knowerId、factId、获知事件、方式 witnessed/heard/inferred、置信/信念状态。玩家知道的线索不会自动复制给所有 NPC；谣言和错误信念可以存在，但必须与世界真相区分。

模型只能提出 NPC 变化，验证器检查人物是否在场、是否接触信息、是否违反锁定设定，以及效果是否允许。存在于合法事件中的“告知”才建立相应知情关系。

离场 NPC 可按游戏时间和已登记目标触发有上限的行动。时钟随玩家行动推进时处理到期任务，不启动按现实时间不断模拟的后台服务；禁止休眠一夜后偷偷改世界。新一轮 NPC 决策包含在当前预算内，模型不能自行增加无限子任务。

## 防止知识串用

区分 GM 内部、玩家已知、指定 NPC、指定阵营四类访问范围，权限由服务端口里的 RoleContext 确定，不能由模型请求参数扩大。

GM 决策可以读取需要的秘密；公开叙述只接收经程序投影的公开状态、公开结果和可见证据，不接收 GM 原始规划文本。NPC 对话只接收该 NPC 的知识/信念与当下可感知内容。读取的片段、计数、标题、错误信息和界面出处遵守同一权限。

生成正文仍需做专有秘密标识和矛盾检测，并经过真实模型对抗评测。上下文隔离能验证“未把不该看的记录交给角色”，不能据此承诺自然语言模型绝不会猜中或产生任何形式的剧透。

## 备份与更新

format1 保持现有五文件、限额、清洗、校验和旧引擎导入导出；新版本继续读写旧备份。

format2 的 manifest 明确 archiveFormatVersion、engineId/Version、eventSchemaVersion、module/rules 的 ID/version/hash、文件清单与摘要。包括初始状态、事件、回合、结果、旁白、人物与事实、知识边、有效记事和完整依赖模组/规则正文；导入后无需原设备上的外部文件。

采用分页读取和流式 ZIP 导出，固定一个战役 revision/事件序号的一致快照。建立完整 staging snapshot 时暂停该战役写入，完成后释放战役锁，再流式打包；不持有长时间数据库写事务。界面显示这段暂停，用户可以取消导出。format2 初始限额为压缩 100 MiB、展开 250 MiB、4,096 ZIP 条目、单 JSONL 行 1 MiB，并按真实读取量校验。

不导出 FTS 缓存、API Key、原模型请求或请求 attempt；导入后显式重新绑定本机模型。引用 ID 必须通过映射整体重建，所有来源链接保持有效。默认只导出已完成或已取消回合的战役；中断回合提示先处理，不默默丢弃它。中断恢复由本机持久化机制负责。

导入验证版本、hash、引用、权限标记、初始状态与事件重放一致性，在新库单事务创建独立战役。坏文件/不支持版本显示明确错误，不能留下半个战役。新格式不伪装为旧格式；0.2 无法读取 format2。

仍使用 io.github.cgm2026.operitrpg、原签名证书、原 MainActivity/更新 FileProvider、CGM2026/OperitRPG 与兼容更新清单。预计版本 0.3.0/code3；正式发布时以当前 latest 为准严格递增。

系统备份白名单增加 rpg-agent.db 及必要选中状态，仍排除模型凭据。长团容量可能超过系统备份配额，跨设备迁移以应用内完整导出为明确验收路径，不声称系统会无限保存资料。

## 关键验收

- 旧库 schema/recordJson、旧 Plan/Action hash 与场景字节未被升级修改；五种中断阶段各有固定样本
- 两个库的选择路由和列表分页正确，不在启动时解码所有历史
- 相同 clientMessageId、并发结算、迟到响应和崩溃恢复均不产生重复效果
- 同一战役 10,000 回合仍分页保存读取，不对整个历史做每轮序列化
- 记忆更正、NPC 谣言、私有秘密和跨战役检索在重启/重建索引后仍正确
- format1 和 format2 分别完成导出导入；format2 在空白安装中能恢复模组依赖和记忆来源
